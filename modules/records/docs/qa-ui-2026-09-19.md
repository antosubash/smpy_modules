### The one BLOCKED case

The brief's exact scenario — "a non-admin role without `records.manage_types`
cannot reach the type editor" — is **not constructible from the browser on this
host**. `users_role` is seeded with a single row (`admin`);
`PUT /api/users/admin/{id}/roles` resolves only role *names that already exist*
(`users/admin/queries.py::_resolve_roles`), and no endpoint in the users or
permissions API creates a role. The per-user grant that the permissions screen
*does* write is ignored by this module (FAIL-5 below), so there is no path to a
"view but not manage" principal at all. It is covered as far as it can be: a
real second user holding nothing is driven through every screen and through the
JSON API from its own browser session, and the guard itself
(`require_manage_types` on `/types/new` and `/types/{key}`) is now present in
`endpoints/views.py`.

## FAILs

### FAIL-1 — every interpolated string in the Records UI renders its raw `{{placeholder}}`

- **Severity** High. Cosmetic in the best case, blocking in the worst (see the
  delete dialog below).
- **Kind** UI bug in `records` (wrong placeholder syntax for this host's i18next
  configuration).
- **Spec** `records-types.spec.ts::the types list counts a type’s live and trashed records`
  and `records-schema-change.spec.ts::removing a field, then re-adding its key, forces a restore-or-discard`
- **Steps** Create a type, add two records, trash one, open `/admin/records/`.
- **Expected** The row reads `1 record (1 trashed)`.
- **Actual** The row reads `{{count}} record({{count}} trashed)`.
- **Screenshots** `bug-i18n-interpolation-types-list.png`,
  `bug-i18n-orphaned-conflicts.png`, `ux-delete-type-count-hidden.png`

**Root cause.** `@simple-module-py/i18n`'s `configureI18n` initialises i18next
with `interpolation: { prefix: '{', suffix: '}' }` — *single* braces. Every
framework catalog follows that (`"{count} files"`,
`"Missing required permission: {permissions}"`). `records/locales/en.json` and
every `defaultValue` in the module's `.tsx` use the i18next default `{{ }}`
instead, so **30 strings** never interpolate. Plural selection still works (the
`_one`/`_other` suffixes resolve); only the substitution fails. Affected keys,
verbatim from the catalog: `types.record_count*`, `types.trashed_record_count*`,
`records.page_info`, `editor.revisions.restore_confirm`,
`editor.revisions.restore_schema_mismatch_detail`, `type_editor.title_edit`,
`type_editor.live_notice`, `type_editor.delete_confirm_description`,
`type_editor.preview.report_summary`, `type_editor.preview.orphaned_conflict`,
`type_editor.preview.apply_anyway`, `type_editor.preview.apply_anyway_description`,
`type_editor.reindex.since`, `type_editor.revisions.version_label`,
`type_editor.revisions.schema_version_label`, `type_editor.revisions.field_count*`,
`type_editor.revisions.restore_confirm`, `fields.unknown_type`,
`validation.min_length`, `validation.max_length`, `validation.decimals`,
`validation.int_digits`, `validation.min`, `validation.max`.

Three places where this stops being cosmetic:

1. **Deleting a type is a guessing game.** The dialog reads `This permanently
   deletes "{{label}}" and its {{count}} record(s) (live and trashed). Type
   {{count}} to confirm.` — it asks the operator to type a number it never
   shows, and does not name the type either. The `DELETE` refuses any other
   number (`confirm_record_count`), so the operator has to go and count the
   records by hand. (`ux-delete-type-count-hidden.png`)
2. **The orphaned-values decision does not say which field it is about.** The
   `SchemaConflictPanel` list renders `{{key}}: {{count}} records still hold a
   removed value` for every entry, so "Restore" / "Discard" is offered with no
   indication of what is being restored or discarded.
3. **Validation messages lose their limits** — "Must be at least {{min}}
   characters", "At most {{scale}} decimal places are stored".

### FAIL-2 — nothing in the Records UI can show a toast: `AdminLayout` mounts no `<Toaster>`

- **Severity** High.
- **Kind** UI bug (a layout/module mismatch that only `records` hits).
- **Spec** `records-crud.spec.ts::confirms a successful save on screen`
- **Steps** Open any record, change a field, press Save.
- **Expected** The "Saved" confirmation `RecordEditor` calls for.
- **Actual** Nothing. `[data-sonner-toaster]` is absent from the DOM on every
  Records screen.
- **Screenshot** `bug-no-toast-feedback.png`

`<Toaster>` is rendered only by `AuthenticatedLayout`
(`@simple-module-py/ui/src/layouts/AuthenticatedLayout.tsx:22`). All four
Records pages use `AdminLayout`, which does not render one, and `records` is the
only module in this repo whose pages do. Every `toast.success` / `toast.error`
in the module is therefore swallowed — including the **error** paths, which have
no other surface:

- `RecordEditor.save()` → `toast.error(err.message)` for anything that is not a
  409 or a 422. A save that fails on a 500 or a network error looks identical to
  one that worked.
- `TypeEditor.save()` → same fallback.
- `TypeRevisions.restore()` → `toast.error(...)` on a failed rollback.
- Success confirmations for a type save, a schema-revision restore and a
  record-version restore.

The only residual feedback after a successful type save is "Preview changes"
going back to disabled, which nobody would read as a confirmation. (The specs
use that, and API polls, instead of a toast — see
`records-helpers.ts::expectTypeSaved`.)

**Watch out when writing tests here:** `page.getByText('Saved')` matches
case-insensitively on a *substring* of an element's combined text, so it happily
matches the `Save`+`Delete` button row ("SaveDelete"). Use `{ exact: true }`.

### FAIL-3 — a soft-deleted record cannot be reached or restored from the UI

- **Severity** High. The delete is advertised as restorable and the editor has
  the UI for it; the UI is unreachable.
- **Kind** UI/route gap — the API supports restore, the admin has no path to it.
- **Spec** `records-crud.spec.ts::a deleted record can be reached and restored from the UI`
- **Steps** Delete a record (from the list row or the editor), then open
  `/admin/records/{key}/{uuid}` again.
- **Expected** The record opens with the "Deleted" badge and the Restore /
  Delete-permanently buttons `RecordActions` renders for exactly that state.
- **Actual** 404. Verified at the API too:
  `GET /api/records/types/{key}/records/{uuid}` → 404, while
  `POST …/{uuid}/restore` → 200.
- **Screenshot** `bug-trashed-record-404.png`

`endpoints/views.py::record_edit` loads through `record_service.get_record`,
which does not carry `execution_options(include_deleted=True)`;
`get_deleted_record` (which does) exists but no view uses it. The record list
has no trashed view either — the filter bar offers no `is_deleted`/trash
switch — so the whole `record.is_deleted` branch of
`RecordEditor`/`RecordActions` (badge, Restore, Delete permanently) is dead code
from the browser's point of view, and the Types list's "(n trashed)" count
points at records nobody can open. Deleting is one-way in the admin.

*Note: a concurrent change landing during this session adds
`deps.py::parse_trashed` and a `?trashed=` listing; it was not wired into the
view at the time of this run, and the spec above is the check for when it is.*

### FAIL-4 — the automatic reindex never completes on SQLite, so an indexed field stays unfilterable

- **Severity** High.
- **Kind** API/backend bug surfacing in the UI.
- **Spec** `records-schema-change.spec.ts::turning on indexing shows the reindex banner until the rebuild clears`
- **Steps** On a populated type, tick `Indexed` on a field that holds values and
  save.
- **Expected** The `ReindexStatus` banner appears and clears within a few
  seconds (it polls `router.reload({ only: ['type'] })` every 5s), after which
  the field can be filtered and sorted on.
- **Actual** The banner never clears. `reindex_pending` still names the field
  after 20+ seconds, and `GET …/records?filter=<field>:eq:…` answers
  `409 {"reason": "reindexing"}` indefinitely.
- **Screenshot** `bug-reindex-never-clears.png`

The background task raises and is logged, not surfaced:

```
ERROR sm_records.services.reindex_runner: records: reindex of type 71 failed
  …
  File "sm_records/services/reindex_runner.py", line 163, in run_pending
    await delete_field_rows(session, rtype, removed)
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
[SQL: DELETE FROM records_index_text WHERE records_index_text.type_id = ? AND records_index_text.field_key IN (?)]
```

The FastAPI background task opens its own session while the request that
scheduled it still holds SQLite's write lock, so step 3 of design §8.5 dies
every time. Reproduced on every index-affecting change I made (field removal
too, not only an `indexed` toggle). It is a `database is locked`, so a Postgres
host may well be fine — but SQLite is this repo's documented default for local
dev (`CLAUDE.md`, `README.md`) and it is what the e2e stack runs on.

The manual recovery does work: `POST /api/records/types/{key}/reindex` (the
banner's "Reindex now" button) clears `reindex_pending` within a second, because
by then the request transaction has committed. So the practical effect is that
**every** index-affecting schema change requires the operator to press "Reindex
now" — which is exactly the state design §8.9 describes as the rare
worker-restart case, not the normal path.

### FAIL-5 — a per-user `records.view` grant has no effect

- **Severity** Medium. The permissions admin screen appears to work and does
  nothing for this module.
- **Kind** Integration bug (wrong `RequiresPermission` imported), surfacing in
  the UI as a 403 after a grant that reported success.
- **Spec** `records-permissions.spec.ts::a direct records.view grant opens the module for that user`
- **Steps** Create a user with no roles, `PUT /api/permissions/users/{id}`
  with `{"permissions": ["records.view"]}` (200, and the response echoes
  `direct: ["records.view"]`), log in as them, open `/admin/records/`.
- **Expected** The Record Types screen.
- **Actual** The 403 error page.
- **Screenshot** `bug-direct-permission-ignored.png`

`sm_records/deps.py` imports `RequiresPermission` from
`simple_module_hosting.permissions`, which resolves permissions from **roles
only** (`resolve_permissions(user.roles, role_map)`). The `permissions` module
ships its own `permissions.deps.RequiresPermission`, documented as "additionally
consults the `permissions_user_permission` table, so a direct grant on a single
user takes effect without inventing a role" — which is precisely what the
permissions screen writes. `ai`, `news` and `pagebuilder` import the hosting one
too, so this is a repo-wide consistency problem rather than something `records`
invented; it is listed here because on this host it is the *only* way to grant
`records.view` (no API creates a role), which makes the module unusable by
anyone but `admin`.

## UX problems that are not bugs

- **No feedback on any successful action.** Beyond FAIL-2: saving a type, saving
  a record, restoring a revision and restoring a schema all complete with the
  page looking exactly as it did. On the record editor the only tell is the
  page title re-deriving from `display_field`.
- **`Delete` on a record is a one-way door with no warning to that effect.** The
  confirm dialog says "Delete this record?" and the delete is in fact reversible
  (soft) — but nothing says so, and nothing can undo it from the UI (FAIL-3).
- **The `indexed` hint is repeated on every field row.** "The single most
  consequential choice on this screen…" appears once per field; on the
  13-field type it is 13 identical paragraphs and stops being read.
- **Relation columns in the list are 8 hex characters.** `RecordCell` renders a
  relation as the first 8 characters of the target uuid, so a list column of
  relations is unreadable. The design doc owns this (expansion is Phase 4), but
  the `RelationPicker` already resolves display titles one screen over.
- **`ne` and the ordered operators disagree about missing values.** On an
  indexed integer field, `qty ne 2` *includes* records that have no `qty` at
  all, while `qty gt 2` / `lt` exclude them and `sort=qty` keeps them and sorts
  them last. All three are defensible and none is explained on screen; a filter
  bar whose "is not" quietly widens the result set is the kind of thing people
  discover from a wrong export.
- **The type editor has no unsaved-changes guard.** "Cancel" navigates straight
  to the list and a half-built 13-field schema is gone with no prompt.
- **Field-type options only appear after a key is typed.** The per-type option
  inputs are keyed on `field-${field.key}-…`; with an empty key they still
  render but every one of them shares the same `id`, so clicking a label focuses
  the wrong row's input while several new fields are in progress.
- **The Types screen is a table, not cards.** Noting only because the brief
  described cards; the table carries the same information.
- **After the concurrent `require_manage_types` change, the types list is a dead
  end for a `records.view` holder** — the row's "Edit" link is still rendered and
  now leads to a 403 page. Not verified in the browser (no such principal is
  constructible, see BLOCKED), read from `endpoints/views.py` + `Types.tsx`.
