## What was changed to make this testable

`tests/e2e/start-test-server.sh` now also writes two records settings through
`scripts/set_setting.py`, the same mechanism the file already used for
`content_locales`:

```
uv run python scripts/set_setting.py sm_records max_count 32 preview_sync_limit 3
```

Both ceilings are unreachable from a browser at their defaults (10,000
records; 5,000 records), and both are DB-backed — `SM_RECORDS_*` is dead by
design — so there is no other way to exercise "10,000+" or the 202 preview
path in a browser test. The values sit **above** every existing fixture
(`records-list.spec.ts` pages through 30 records and asserts an exact total;
`records-schema-change.spec.ts` previews a type holding two), so no existing
spec changes meaning. Confirmed by a cold run of the whole records suite.

**No component was changed.** Every `data-testid` the new specs use already
existed; **no testids were added**.

## FAILs

### FAIL-1 — the import dry run does not predict the refusal an apply hits (severity: **major**)

The one workflow import/export exists for — export, edit in a spreadsheet,
import back — reports success in the preview and then fails on apply. The
export deliberately carries no `version` (README § Import and export), and
`write_row` refuses an update whose row has none; but that check lives in the
*write*, which a dry run skips, so `plan_rows` counts the row as "to update".
`services/import_.py`'s own docstring claims the two paths are one function
"with the writing step switched off" — this is the place they are not.

Steps (admin, any type with one text field and one record):

1. `/admin/records/{key}` → Export → Download JSON.
2. Change one `data` value in the file (nothing else).
3. Import → pick the edited file.

Expected: the dry run reports what the apply will do — here, `1 failed` with
the "no version" message, so the operator learns it before pressing a button
that writes.

Actual: the preview says `1 row(s): 0 to create, 1 to update, 0 unchanged, 0
failed` and offers **Apply import**; the apply then answers `1 row(s): 0 to
create, 0 to update, 0 unchanged, 1 failed` with

```
Row 0 (—): record 012fe3cd… already exists and the file carries no 'version';
re-export it, add a version column, or import with force=true
```

and nothing is written (verified: the record still reads `Original`).

Screenshots: `shot-edited-export-dryrun.png`, `shot-edited-export-apply.png`.

Two things ride along with it:

- **"Row 0"** — the failure is attributed to row 0, which no file has. The
  error is raised out of `_write`'s `abort` path, where `import_records`
  appends `ImportRowError(row=0, …)`; the file's own row number is available
  (`plan.row.number`) and is what a spreadsheet user needs. `field` renders as
  the em dash placeholder for the same reason.
- **No way forward from the UI.** The message's three remedies are
  "re-export it" (which produces the same version-less file), "add a version
  column" (hand-editing JSON/CSV), or `force=true` — and `RecordIoMenu`
  exposes no `force`, `mode`, `on_error` or `match_by` at all. So a bulk edit
  cannot be completed in the browser by any route.

## UX problems

**UX-1 — the record list does not refresh after "Apply import".** `RecordIoMenu.run`
sets the report and toasts; nothing calls `router.reload({ only: ['records'] })`.
After applying an import that created two records the list behind the dialog is
still empty, and closing the dialog leaves it empty — the operator has to reload
the page to see the rows they just imported. (The toast "Import applied" does
appear: `shot-import-applied.png`.)

**UX-2 — the capped footer's range contradicts the rows on screen, and the "+"
is unexplained.** With `max_count = 32` and 33 records, page 2 renders 8 rows
under "Showing 26–32 of 32+" (`shot-capped-page2.png`) — the range end is
`min(page*pageSize, total)` and `total` is the cap, so it is one short of the
rows it is describing. Separately, nothing on the screen says what "32+" means
(in production, "10,000+"): there is no tooltip and no help text explaining
that the count stopped rather than the data. An operator's reasonable reading
of "10,000+" plus a `Next` button that is disabled is "the list is broken".

**UX-3 — an import gives no feedback while it runs.** From picking the file to
the report dialog opening there is nothing: the "Import" button is disabled but
keeps its label, no spinner, no "Checking…" (`shot-import-inflight.png`, taken
with the response held for 3s). The dry run is the one operation in the module
that can touch every record of a type, and on a large file it can take minutes —
the screen looks idle for all of them. The schema preview solved exactly this
problem with a label on its own button; the import did not.

**UX-4 — a preview job the server no longer holds shows an internal sentence.**
Intercepting the poll with a 404 (what a worker restart, a multi-worker host or
the TTL produces) puts `no schema preview job 'abc' for 'job404'` on screen, as
a `role="alert"` (`shot-preview-job-404.png`). The module already has the right
copy for this — "The check could not be completed. Try previewing again." — but
it is only used for `status: failed`; a 404 lands in the raw-`error` branch.

**UX-5 — parse failures speak to a developer.** A `.txt` upload answers *"cannot
tell whether this is JSON or CSV: send ?format=, a .json/.csv filename, or
Content-Type: application/json / text/csv"* and a truncated JSON file answers
*"the file is not valid JSON: Expecting property name enclosed in double quotes
at line 1, column 3"* (`shot-import-txt.png`, `shot-import-broken-json.png`).
Both are visible and both are accurate; neither is phrased for the person who
just picked a file. The first mentions a query parameter no browser user can
send.

**UX-6 — a type's collection is invisible outside its editor.** The Record Types
list shows Label / Key / Records only (`shot-types-list.png`). Which types are
partitioned — the thing a migration, a backup and a reindex all care about — can
only be discovered by opening each type. A column, or a badge next to the key,
would cost nothing.

**UX-7 — the "Translatable" toggle keeps a value the server refused.** After the
409, the switch stays in the rejected position next to the error explaining that
the change did not happen; only a reload puts it back. The error text is good
("holds 1 record(s) in a locale other than 'en'; translating them away or
deleting them is what makes 'translatable' safe to turn off") but the control
above it disagrees with it.

**UX-8 — the locale badge's explanation is a `title` tooltip.** "This record's
language is fixed for its lifetime." is the answer to the question the editor
provokes ("why can't I change the language?"), and it is reachable only by
hovering a mouse — not on touch, not by keyboard. The new-record screen has a
Language select and the edit screen simply has none, with no inline sentence
saying why.

**UX-9 — the Languages panel never explains a disabled "Add".** The brief asked;
the answer is that the panel has no long-lived disabled state to explain —
`Add translation` is disabled only while another one is being created (it then
reads "Creating…"), and a taken language renders "Open" plus the sibling's
title/status instead of a disabled button. What is missing is smaller: a failed
`POST` (e.g. a sibling created in another tab meanwhile) surfaces the raw server
message in `records-translations-error`, and the panel is not re-fetched, so the
row keeps offering "Add" for a language that now exists.

**UX-10 — the import report's wording stays in the future tense after the
write.** The result dialog says "2 row(s): 2 **to create**, 0 to update, 0
unchanged, 0 failed" for rows it has already created. `skipped` is rendered as
"unchanged", which is the clearest word for it — that part reads well — but a
result and a preview should not share one sentence.

**UX-11 — a trash export cannot be re-imported.** `Export` in the Trash view
correctly carries `trashed=true` and produces a file of the trashed records, but
importing that file back is refused per row ("record … is in the trash; restore
or purge it first"). It is a defensible rule; it just makes that particular
export a file with no consumer, and nothing on the screen says so.

**UX-12 (minor, testability) — duplicate accessible names in the record table.**
A field labelled "Title" produces a second sortable header whose accessible name
is exactly the display-title column's ("Title"), so `getByRole('button', {name:
'Title'})` is ambiguous and a screen-reader user hears the same name twice in
one row of headers. `records-collections.spec.ts` works around it by labelling
its field "Event title".

## Note on the "Checked N of M" assertion

The deferred preview is genuinely exercised end to end (the browser really gets
a 202 and really polls), but the progress *label* cannot be caught by a race-free
assertion against a type a browser test can seed: nine records are scanned in
single-digit milliseconds, so the first poll already finds `status: done`.
`records-preview.spec.ts` therefore asserts the label against one intercepted
poll carrying the exact `SchemaPreviewJobRead` shape the server sends while a
scan runs, and lets every later poll through to the real job. If the poll
contract ever changes shape, that test keeps passing while the real one would
not — the sibling test asserting the 202 and the real report is what guards that.
