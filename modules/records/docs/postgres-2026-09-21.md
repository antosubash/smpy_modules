# Records on Postgres — migrations, unit suite, write path, concurrency, e2e

## 0. Headline

* **Three migration bugs made a Postgres install impossible from an empty
  database.** Not one of them is in `records`: a boolean `server_default` of
  `0`, an enum `server_default` naming a value where SQLAlchemy stores the
  name, and two `pagebuilder` revisions whose `downgrade` dropped their tables
  and left their enum *types* behind. The chain now applies, round-trips and
  `alembic check`s clean.
* **`alembic check` was only ever clean on SQLite because SQLite cannot see the
  drift.** `users.models.user` has always declared
  `Index("ix_users_user_email_lower", text("lower(email)"))` and no revision
  ever created it. SQLAlchemy cannot reflect expression indexes on SQLite, so
  the comparison is skipped with a warning; Postgres reflects it, finds
  nothing, and fails. Revision `d2b7a1c4e905` creates it on both.
* **The module itself needed no changes.** 927 unit tests, 49 perf
  measurements and 109 Playwright specs all pass on Postgres. The one unit
  failure was the test *harness* — two fixtures that are separate `:memory:`
  databases on SQLite are one database on Postgres — not module code.
* **The per-type lock holds.** Twenty concurrent `create_record` calls on one
  `unique` value from twenty separate sessions: one 201, nineteen 409s, one
  row, no `IntegrityError`, no deadlock. This is the first time the
  `SELECT … FOR UPDATE` branch of `lock_type` has been *executed* rather than
  compiled — `tests/test_unique_concurrency.py` races on a SQLite file and
  cannot reach it.
* **The write path is cheaper on Postgres, in statements as well as
  milliseconds** — and this is the one place where the study's standing claim
  that "statement counts are a property of the code and travel" is wrong. A
  create costs **10 statements on Postgres and 13 on SQLite**, and the gap
  grows with the number of indexed fields, because index rows batch into one
  `INSERT` per *kind table* on Postgres and one per *row* on SQLite. See §5.
* **The perf suite can now measure all of itself on Postgres.** 19 of its 49
  measurements used to skip, because `perf_db_copy` copies a file. It now uses
  `CREATE DATABASE … TEMPLATE` on Postgres, which closes the "still not
  verified" list the 2026-09-19 study ended with: schema operations, import
  and export, the reindex, content i18n and the reduce index all have Postgres
  numbers below.

## 2. Migrations

Run from the repo root as `alembic -c host/alembic.ini`, against an empty
`records_e2e`.

| step | result |
|---|---|
| `upgrade heads` on an empty database | **22 revisions**, clean — after the three fixes in §2.1–§2.3 |
| `alembic check` | clean — after §2.4 |
| `downgrade records@base` | **22 downgrades**, database emptied to `alembic_version` |

| `upgrade heads` again | 22 revisions, clean |
| `alembic check` again | clean |
| offline `--sql`, records range | 4 `CREATE TYPE`, 19 `CREATE TABLE`, 70 indexes, no SQLite artefacts |

| the same round trip on SQLite | 22 / 22 / 22, `check` clean, index present |

`downgrade records@base` walking **every** revision rather than only
`records`'s is the behaviour `CLAUDE.md` already documents, and it reproduces
exactly on Postgres. Nothing here changes that.

### 2.1 `users_user.is_external` — a boolean defaulted to the integer `0`

```
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.DatatypeMismatch)
column "is_external" is of type boolean but default expression is of type integer
```

`host/migrations/versions/ed06f4584f6b_initial.py` wrote
`server_default=sa.text('0')`. SQLite has no boolean type and stores `0`
happily; Postgres type-checks the default expression against the column and
refuses the `CREATE TABLE`. **This is the first statement of the first
revision, so no Postgres install of this host has ever got past it.**

Fixed to `sa.false()`, which renders `false` on Postgres and `0` on SQLite —
the same literal the five other boolean defaults in this history already use.

*Classification: real bug, host migration, not `records`.*

### 2.2 `pagebuilder_revision_event` — a default naming the enum's value, not its name

```
sqlalchemy.exc.DataError: (psycopg2.errors.InvalidTextRepresentation)
invalid input value for enum pagebuilder_revision_event: "publish"
```

`PageRevision.event` is declared
`Column(SAEnum(RevisionEvent, name="pagebuilder_revision_event"), …,
server_default=RevisionEvent.PUBLISH.value)`. `SAEnum` over a Python enum
persists the member **name** (`PUBLISH`), so the type is
`ENUM('PUBLISH', …)` while the default is the lower-case `'publish'`. On
SQLite the enum is a `VARCHAR` and the mismatch is invisible; on Postgres the
default is not a member of the type.

Fixed in both places that state it — `RevisionEvent.PUBLISH.name` in
`modules/pagebuilder/pagebuilder/models/_page.py` and `server_default='PUBLISH'`
in `4cf1b4c9f8f9`. `env.py` does not set `compare_server_default`, so neither
edit shows up as autogenerate drift, and the rendered SQLite DDL is unchanged
in meaning.

*Classification: real bug, `pagebuilder` model + migration, not `records`.*

### 2.3 Four `pagebuilder` enum types survived their own `downgrade`

After `downgrade records@base` the database held no tables and four types:

```
pagebuilder_page_status  pagebuilder_revision_event
pagebuilder_snapshot_source  pagebuilder_import_status
```

and the next `upgrade` died on
`DuplicateObject: type "pagebuilder_page_status" already exists`.
`op.drop_table` builds a bare `Table` with no type metadata, so on Postgres
`DROP TABLE` leaves the `CREATE TYPE` behind.

`records` does not have this bug: `e23090832709` and `3b4733cf5444` already
carry a `_drop_enums` helper, added for exactly this case, and their four
types were gone. The two `pagebuilder` revisions that create enums got the
same helper, copied rather than imported so each revision keeps working if the
ones around it are squashed.

*Classification: real bug, `pagebuilder` migrations, not `records`. The
`records` fix this was supposed to exercise works.*

### 2.4 `ix_users_user_email_lower` never existed

`alembic check` on Postgres:

```
Detected added index 'ix_users_user_email_lower' on '()'
FAILED: New upgrade operations detected: [('add_index', …)]
```

`users/models/user.py` declares
`__table_args__ = (Index("ix_users_user_email_lower", text("lower(email)")),)`
and nothing in this host's 22 revisions creates it. **It has been missing from
every deployed database since the initial revision**, and the reason nobody
noticed is dialect-specific: SQLAlchemy cannot reflect expression-based
indexes on SQLite, so `alembic check` there prints

```
UserWarning: autogenerate skipping metadata-specified expression-based index
'ix_users_user_email_lower'; dialect 'sqlite' … can't reflect these indexes
```

and then reports "No new upgrade operations detected". A clean `check` on
SQLite was never evidence.

Added as revision `d2b7a1c4e905`, on both dialects — SQLite supports
expression indexes even though it cannot reflect them, and creating it there
keeps the two schemas the same shape instead of encoding the reflection gap
into the migration history. This moves the head; `records`'s own branch label
is untouched.

*Classification: real gap, framework model vs host migrations, surfaced only
by Postgres.*

### 2.5 Offline `--sql` from `base` stops at a data migration

`alembic upgrade base:heads --sql` fails inside `b1f4a72c9d30`
(`add page locale and translation group`) at
`sa.inspect(bind).has_table(_SETTINGS_TABLE)` —
`NoInspectionAvailable: … MockConnection`. A migration that reads the database
to decide what to do cannot run in offline mode, on any dialect. This
pre-dates `records` and was left alone.

The records range generates fine (`upgrade b1f4a72c9d30:heads --sql`), and the
output is right for the dialect: four `CREATE TYPE`, the partial unique index
as `… WHERE slug IS NOT NULL` with no `sqlite_where` leaking, and the
descending indexes as `… DESC NULLS LAST`.

```bash
cd modules/records

  ../../.venv/bin/python -m pytest -q -p no:cacheprovider
```

| run | result |
|---|---|
| Postgres, first run | **926 passed, 1 failed** in 212 s |
| Postgres, after the harness fix + 4 new tests | **931 passed** in 238 s |
| SQLite, same tree | **927 passed, 4 skipped** in 184 s |

The four extra are `tests/test_postgres_lock.py` (§4), which skips on SQLite.
The SQLite count and timing are unchanged from before this work.

### 3.1 How the opt-in works

`simple_module_test`'s fixtures and this module's `conftest.py` both hard-code
in-memory SQLite, so a new module, `tests/pg_support.py`, owns the decision:

* `RECORDS_TEST_URL` unset (**the default, so CI is unchanged**) — in-memory
  SQLite on a `StaticPool`, byte for byte what `conftest.db_state` built
  before.
* `RECORDS_TEST_URL=postgresql+asyncpg://…` — that database, with the schema
  created once per process and `TRUNCATE … RESTART IDENTITY CASCADE` per test.

`RESTART IDENTITY` is load-bearing and not tidiness. `conftest._clear_model_cache`
exists because every test's `:memory:` database hands out `type_id` 1 afresh
and the compiled-validator cache is keyed on type id; a Postgres database
whose sequences kept climbing would quietly break the assumption that fixture
is written against. `alembic_version` is excluded, so a database that was
migrated rather than `create_all`-ed still looks migrated.

A fresh engine per test, not a session-scoped one: `asyncio_mode = "auto"` with
the default function loop scope gives every test its own event loop, and an
asyncpg pool belongs to the loop that made it. `tests/perf/conftest.py` records
the same reasoning for `perf_db`.

### 3.2 The one failure

```
FAILED tests/test_collections_crud.py::
  test_a_trashed_collection_record_is_hidden_from_a_plain_select
  → KeyError: 'uuid'   (the POST that should have returned 201 did not)
```

It is the only test in the suite that takes **both** `client` (whose app owns
a database built by `app_harness.build_app`) and `db_state` (built by
`conftest.db_state`). On SQLite those are two independent `:memory:`
databases and the second is simply unused. Against one Postgres database they
are two engines over the same tables, and the second fixture's truncation
emptied what the first had seeded — the type the request was posting to was
deleted out from under it.

*Classification: the test harness assumes SQLite. No module code involved.*

Fixed in the harness rather than in the test: `pg_support.arm_reset()` is
called by an autouse fixture once per test, and only the **first**
`make_db_state` of a test truncates. A later one in the same test is a second
window onto the same data, which is as close to the SQLite behaviour as one
database can get. The test is untouched.

### 3.3 Differences that did *not* materialise

The brief listed likely SQLite-only assumptions. For the record, none of these
needed a change:

* **Statement counts including `UPDATE … SET version = version`.** No unit
  test asserts a statement count; the counts live in the perf suite, which
  reports rather than asserts them. The difference is real and is §5.
* **`include_deleted` on Core columns, JSON comparison, case folding,
  `ANALYZE`.** All pass unchanged. `analyze_tables` is already a deliberate
  no-op off SQLite.
* **`tests/perf/_schema.py`.** Already backend-independent since finding S2;
  it uses `inspect()` rather than reading `sqlite_master`.

## 4. Concurrency — the per-type lock

`tests/test_postgres_lock.py`, new, skipped unless `RECORDS_TEST_URL` names a
Postgres database. Twenty writers, each on its own session and therefore its
own connection, through the service layer rather than an HTTP client so that
the request pipeline's own commit ordering cannot explain a pass.

| case | result |
|---|---|
| 20 creates, same `unique` value, field is not the `slug_field` | **1 created, 19 `Conflict`, 1 row stored, 0 `IntegrityError`** |
| 20 creates, same value, field **is** the `slug_field` | 1 created, 19 `Conflict`, 1 row, no `IntegrityError` escaped |
| 20 creates, 20 distinct values | 20 created, 20 rows — no deadlock, no lost writer |
| `update_type` (adds a field) racing 20 creates | edit lands or loses as a `Conflict`; every stored record carries `schema_version` ∈ {before, after} and a payload the corresponding version declares |

The first row is the one that matters. `unique` cannot be a database
constraint here — the index tables are shared across every field of a kind, so
a unique index naming a runtime-chosen field key is not expressible — so
nothing but `lock_type`'s `SELECT … FOR UPDATE` stands between twenty writers
and twenty rows. It holds. Every run completed well inside its 60-second
`wait_for`; nothing deadlocked.

The schema-edit case deliberately asserts a property and not an order: how
many creates land, and whether the edit wins, are races, and pinning either
would make it a test of the scheduler.

**What remains SQLite-only:** `tests/test_unique_concurrency.py` and
`tests/test_reindex_runner_locking.py` build their own file-backed SQLite
database (`file_db`) and ignore `RECORDS_TEST_URL` — deliberately, since what
they pin is the *SQLite* branch of the lock. The new file is the Postgres
counterpart, not a replacement.

## 5. Perf — SQLite vs Postgres

`RECORDS_PERF_N=20000`, `REPS=20`, p50 through the real endpoints, both
backends measured in the same session on the same machine.
`RECORDS_PERF_URL=postgresql+asyncpg://…` selects the backend.

Row counts differ slightly between the two seeded databases (the seeder's
split is random), so `order` is 9,000 rows on SQLite and 8,968 on Postgres.
Ratios below are Postgres ÷ SQLite: **under 1.00 means Postgres is faster.**

### 5.1 Write path — fewer statements, and fewer milliseconds

| operation | SQLite p50 | PG p50 | ratio | stmts SQLite → PG |
|---|---|---|---|---|
| `create_record(company)` | 11.91 ms | **8.60 ms** | 0.72× | **13 → 10** |
| `create_record(product)` (has a `unique` field) | 14.02 ms | **10.04 ms** | 0.72× | **14 → 10** |
| `update_record` (no indexed change) | 18.06 ms | **13.22 ms** | 0.73× | **20 → 16** |
| `update_record(price)` | 20.01 ms | **13.18 ms** | 0.66× | **21 → 17** |
| trash → restore → trash → purge | 46.18 ms | **30.62 ms** | 0.66× | **46 → 40** |
| `create_record`, 1 reduce spec (steady) | 15.40 ms | **9.23 ms** | 0.60× | **14 → 11** |
| `update_record`, 1 reduce spec, group unchanged | 19.25 ms | **11.82 ms** | 0.61× | **20 → 17** |

**These are the only statement-count differences in the whole suite**, and they
all come from one place: `write_index`.

Captured directly, one create, one `text` index row per field plus one
`integer`:

| indexed `text` fields | SQLite total / index stmts | Postgres total / index stmts |
|---|---|---|
| 1 | 7 / 2 | 7 / 2 |
| 2 | 8 / 3 | **7 / 2** |
| 4 | 10 / 5 | **7 / 2** |
| 8 | 14 / 9 | **7 / 2** |

On Postgres the ORM emits one `INSERT … SELECT` per *kind table* — at most six,
whatever the type looks like. On SQLite it emits one
`INSERT … VALUES (…) RETURNING id` per *row*. So a create is **O(indexed
values) in statements on SQLite and O(kind tables touched) on Postgres**, and
the published "13 statements per create" is an SQLite number for the demo
`company` type, not a constant.

Everything else about the write path travels: `lock_type` is one statement on
both (`UPDATE records_type SET version = version` vs
`SELECT … FOR UPDATE`), `ensure_unique` is the one extra `SELECT` on both, and
the revision trim and payload insert are unchanged.

### 5.6 Where Postgres is *slower*

Four measurements, all of them bulk index rewrites:

| operation | N | SQLite | PG | ratio |
|---|---|---|---|---|
| `reindex store`, batch = 500 | 2k | 433.74 ms | **672.09 ms** | 1.55× |
| `reindex store`, batch = 2000 | 2k | 504.16 ms | 669.60 ms | 1.33× |
| `display_field` change, whole-type rebuild | 2k | 932.40 ms | **1309.39 ms** | 1.40× |
| `_orphaned.count_conflicts` / `.discard` | 2k | 44.25 / 258.34 ms | 69.11 / 332.81 ms | 1.56× / 1.29× |

`reindex store` at batch = 100 is a wash (837 vs 854 ms), so the gap is not
per-statement latency; it is the bulk `DELETE` + re-`INSERT` of index rows
costing more against a table with real MVCC and real indexes than against a
SQLite file. The rate is still 2,965 rec/s at batch 500, comfortably inside
what `reindex_stale_after_seconds` is set against, and the reindex is a
background job. **Not treated as a defect**; recorded so nobody reads the
SQLite figure as a Postgres promise.

### 5.7 Plans, by `EXPLAIN (ANALYZE, BUFFERS)`

Three hottest read queries, against the 8,968-row `order` type.

**Sort by a `ref` field** — 34.97 ms p50 through the endpoint, 14.98 ms in SQL:

```
Limit (actual time=14.935..14.942 rows=25 loops=1)
  ->  Sort  Sort Key: records_index_ref_1.target_uuid, records_record.id
        Sort Method: top-N heapsort  Memory: 63kB
        ->  Hash Left Join (actual time=4.948..10.250 rows=8968)
              Hash Cond: (records_record.id = records_index_ref_1.record_id)
              ->  Bitmap Heap Scan on records_record  (rows=8968)
                    ->  Bitmap Index Scan on ix_records_record_type_id
              ->  Hash (rows=8968)
                    ->  Seq Scan on records_index_ref
                          Filter: (field_key = 'customer')
                          Rows Removed by Filter: 33938
```

The whole type is materialised before the `LIMIT`, which is what a sort on a
joined column requires and what F5 already describes. Postgres does it with a
hash join and a top-N heapsort rather than a temp B-tree; the index-table side
is a `Seq Scan` because it wants 8,968 of 42,906 rows (21 %) and an index would
not pay. **No SQLite-specific trap reproduces** — which is what the
2026-09-19 round predicted but could only check for the read path.

**Datetime range filter** — 28.16 ms p50, **0.44 ms in SQL**:

```
Limit
  ->  Nested Loop Semi Join (actual time=0.346..0.416 rows=25)
        ->  Index Scan using pk_records_record on records_record  (rows=55)
              Filter: (is_deleted IS FALSE) AND (type_id = 5)
        ->  Index Scan using ix_records_index_datetime_record  (loops=55)
              Filter: value >= '2024-01-01…' AND type_id = 5 AND field_key = 'placed_at'
```

The semi-join of F1, nested rather than hashed. Note the gap between 0.44 ms
of SQL and 28 ms of request: at this size the read path is Python and
serialisation, not the database.

**Bounded count, `cap` well below the type** — the one plan that reads
`records_record` sequentially:

```
Aggregate
  ->  Subquery Scan on anon_1  Filter: (anon_1.is_deleted IS FALSE)
        ->  Limit  (rows=2990)
              ->  Seq Scan on records_record  Filter: (is_deleted IS FALSE) AND (type_id = 5)
```

SQLite drives this from `ix_records_record_type_published_desc`. Postgres
chooses a sequential scan and is **faster anyway** (1.49 ms vs 2.57 ms): the
`LIMIT` stops it after 2,990 qualifying rows and a sequential read has no
random I/O to pay. Above the cap it switches to a `Bitmap Heap Scan` on
`ix_records_record_type_id`. The soft-delete filter stays *inside* the `Limit`,
which is the property F4 goes out of its way to keep — that is the thing to
check here, and it holds. The 2026-09-19 claim that "no plan anywhere reads
`records_record` sequentially" was made over the read path only and should be
read with this exception.

### 5.8 Two instrument fixes were needed first

* **`plan_label` reported `?` for every Postgres row.** It extracted index
  names by splitting on SQLite's upper-case `USING`; Postgres writes
  `Index Scan using ix_… on t` in lower case. The plan column — most of why
  the table exists — said nothing on the first Postgres run. Now handles both,
  with the SQLite label left byte-for-byte identical so numbers already in
  `performance.md` stay comparable.
* **`perf_db_copy` skipped 19 of 49 measurements on Postgres**, because it
  copies a SQLite file. It now uses `CREATE DATABASE … TEMPLATE` (autocommit,
  after disposing the template's engine, dropped afterwards), which is the
  same operation by the server's own means. This is what makes §5.5 and §5.6
  exist.

### 13.1 `b1f4a72c9d30` is offline-safe now

§2.5 recorded that `alembic upgrade base:heads --sql` died inside this
revision on `sa.inspect(bind).has_table(...)` — `MockConnection` has no
inspector. Two things in it read the database, and both now branch on
`op.get_context().as_sql`:

* **the default content locale** — the settings table cannot be queried, so
  offline emits the class default `'en'` as a literal, and the revision's
  docstring says an operator on a differently-configured install has to edit
  it;
* **the `translation_group` backfill** — a per-row `uuid4()` loop needs the
  rows. It would have emitted *no* `UPDATE` at all offline, leaving the column
  NULL and making the `SET NOT NULL` two statements later fail on any
  non-empty table. Offline emits one set-based statement instead,
  `SET translation_group = 'p' || CAST(id AS VARCHAR)`, which is unique per
  row, spelled identically by both dialects, and as opaque as the uuid it
  replaces.

**Online behaviour is byte-for-byte unchanged**; both branches are taken only
when `as_sql` is true. The full chain still round-trips online on both
dialects after the edit (§12).

### 13.2 SQLite offline is a dead end, and not this repo's fault

It stops at the *first* revision that uses `op.batch_alter_table` —
`af06f6ea093e`, long before records — with

```
This operation cannot proceed in --sql mode; batch mode with dialect sqlite
requires a live database connection with which to reflect the table
"pagebuilder_pages".
```

SQLite has no `ALTER COLUMN`, so batch mode rebuilds the table, and writing
that `CREATE TABLE` without a database means handing Alembic the table as a
`copy_from=` `Table`. Six revisions use batch mode across **26 call sites**,
each needing a hand-written copy of that table *as it stood at that point in
history*. That is not a small change and it was not made. A SQLite host
migrates online; Postgres is where an offline script is wanted anyway.

### 18.2 `records-crud.spec.ts:281` — a framework race Postgres's commit latency can open

```
Error: POST /types/rel_mubhuf56_twgc/records → 404:
       {"detail":"no record type with key 'rel_mubhuf56_twgc'"}
   at seedSinkType (records-crud.spec.ts:66)
```

`seedSinkType` does two strictly sequential awaited requests: create a type,
then create a record on it. The second got a 404. The server log explains it:

```
17:03:00.916  db.entity.created RecordType            (correlation d490440a…)
              POST /api/records/types              → 201
              POST /api/records/types/rel_…/records → 404
17:03:00.931  request.completed  …/records   404   duration 4.82 ms
17:03:00.935  db.session.commit  (d490440a…)        db_duration_ms 24.01
17:03:00.936  request.completed  /api/records/types 201  duration 25.82 ms
```

**The 201 reached the client before its transaction committed.** This build of
the framework — `simple_module_core` / `db` / `hosting` **0.0.26**, what this
repo pins — commits in `simple_module_db.deps.get_db`'s *exit code*, and
FastAPI runs a `yield` dependency's exit code **after** the response has been
delivered. There is no `CommitBeforeResponseMiddleware` in 0.0.26; that is the
fix for upstream `antosubash/simple_module_python#257` and it lives in a newer
framework build than this repo pins.

So the window between "client has the 201" and "the row is visible" is exactly
the commit's duration. On SQLite that is a fraction of a millisecond and the
client effectively never wins the race. On Postgres it is normally ~1 ms — and
it was **24 ms here because the cluster was simultaneously running a 20,000
record seed for §19**, which is the author's fault, not the suite's.

**Re-run on its own, on an idle cluster, the spec passes** (13 passed / 1
failed, the failure being §18.1 again). Classification: **not a records bug,
not a Postgres bug — a latent framework ordering bug that Postgres's larger
commit latency makes reachable, and that this run made reachable by loading
the cluster.** It is worth knowing that it exists: any host on framework
0.0.26 that creates something over the API and immediately reads it back in a
second request is running on that margin, and the margin narrows as the
database gets busier.

*Lesson for the next person: do not run anything else against the cluster
while the e2e suite is on it. The suite is single-worker and its assertions
are about ordering.*

## 19. Sustained writes and autovacuum

The open item §10.5 left: *"anything about a Postgres cluster under real
concurrency — connection-pool sizing, autovacuum behaviour on the index tables
under sustained writes."* Half of it is answered here; the concurrency half is
still open.

Database `records_vacuum`, migrated to head, then:

1. `seed --records 20000 --reset` — 20,000 records, **182.2 s (110/s)**:
   company 1,000 / contact 5,000 / product 3,000 / store 2,000 / order 9,000;
2. `reindex --type <t>` for all five types — 1.9 / 3.3 / 2.9 / 2.4 / 6.7 s,
   which rewrites **every index row of every type**;
3. three rounds of `update_record` over 5,000 `order` records, through the
   service layer, each round a fresh session per record.

Cluster settings are `initdb` defaults throughout — `autovacuum = on`,
`autovacuum_vacuum_scale_factor = 0.2`, nothing tuned.

### 19.1 Throughput does not decay

| round | updates | wall | rate |
|---|---|---|---|
| 1 | 5,000 | 82.1 s | **61/s** |
| 2 | 5,000 | 83.1 s | 60/s |
| 3 | 5,000 | 82.0 s | **61/s** |

Flat across 15,000 updates. Whatever bloat accumulates, it does not reach the
write path within this workload.

### 19.2 `pg_stat_user_tables`, before and after the three rounds

"Before" is after the seed and the full reindex, so it shows what the *reindex*
leaves behind; "after" is immediately at the end of round 3.

| table | live | dead before | dead after | last autovacuum before → after | autovacuums |
|---|---|---|---|---|---|
| `records_record` | 20,000 | 0 | **3,028** | 17:18:18 → 17:22:18 | 7 → 11 |
| `records_index_text` | 64,506 | 27,000 | **15,378** | 17:18:18 → 17:21:18 | 8 → 10 |
| `records_index_ref` | 42,952 | 35,957 | **5,765** | 17:18:18 → 17:22:18 | 8 → 12 |
| `records_index_number` | 16,000 | 9,000 | 1,506 | 17:18:18 → 17:22:18 | 8 → 12 |
| `records_index_datetime` | 9,000 | 9,000 | 1,506 | 17:18:18 → 17:22:18 | 7 → 11 |
| `records_index_date` | 8,000 | 0 | 0 | 17:18:18 (untouched) | 4 |
| `records_index_bool` | 9,000 | 0 | 0 | 17:18:18 (untouched) | 4 |

**Autovacuum kept up, and comfortably.** Every table that was written to was
autovacuumed *during* the rounds — four more passes on most of them — and every
`last_autovacuum` is within the last minute of a four-minute workload. Dead
tuples never exceed 24 % of live (`records_index_text`), which is where the
default 20 % scale factor plus its 50-row floor puts the next trigger: the
counter is a sawtooth, not a ramp. Two tables (`date`, `bool`) hold fields the
update never touches and show exactly zero churn, which is the index layer
doing what it claims — a write only rewrites the kind tables whose values
changed.

**The reindex is the dirtier operation, not the sustained writes.** Look at the
"before" column: the full reindex left 35,957 dead rows on `records_index_ref`
and 27,000 on `records_index_text` — more than 15,000 record updates produced —
because it is a bulk `DELETE` + re-`INSERT` of every index row. This is the
same asymmetry §5.6 measured in milliseconds, now visible in tuples. It is
still a background job, and autovacuum had cleared most of it by the end.

`records_record.n_tup_upd` moved 6,696 → 36,652 across 15,000 `update_record`
calls: **two row updates per logical update**, which is `guarded_bump`'s
optimistic-version `UPDATE` plus the write itself.

### 19.3 Plans do not degrade

`EXPLAIN (ANALYZE, BUFFERS)` on the same two statements before and after.

**List page 1 of `order` (9,000 rows), default sort:**

| | before | after |
|---|---|---|
| plan | `Index Scan Backward using ix_records_record_type_created_id` | **identical** |
| shared buffers | 6 | 5 |
| execution | 0.078 ms | **0.041 ms** |

The F11/S2 index does its job on both sides: 25 rows read, nothing sorted,
nothing else touched.

**Three ANDed filters (`order_status` eq, `total` gte, `placed_at` gte):**

| | before | after |
|---|---|---|
| plan | `Nested Loop Semi Join` × 2 over the index tables, top-N heapsort | **same shape** |
| entry point | `Index Scan using ix_records_index_text_lookup` | `Bitmap Heap Scan` on the same index |
| shared buffers | 14,406 | 15,019 |
| execution | 14.867 ms | **12.884 ms** |

F1's semi-join structure survives intact. The one difference is the planner
switching the most selective leg from a plain index scan to a bitmap heap scan
over the *same* index — a costing choice after the autoanalyses, and it came
out 13 % faster, not slower.

**Verdict: no degradation on either statement, and autovacuum kept up at
`initdb` defaults for this size and shape of workload.** What is still not
tested is many writers at once; see §22.

## 20. Connection pool against the cluster

`simple_module_db.session.init_db` defaults, which
`simple_module_hosting.app_builder` passes from `HostSettings`:

| setting | value |
|---|---|
| `db_pool_size` | 10 |
| `db_max_overflow` | 20 |
| `db_pool_pre_ping` | true |
| `db_pool_recycle` | 1800 s |

So **one worker process can hold up to 30 connections**. This cluster runs the
`initdb` default `max_connections = 100`, three of which are reserved for
superusers — 97 usable. Four saturated workers (120) exhaust it; three (90)
just fit with nothing spare for `psql`, the CLI or a migration. An install
running more than three workers per cluster has to raise `max_connections`,
lower `db_pool_size`/`db_max_overflow`, or put PgBouncer in front. None of
this is new behaviour — it is simply the first time the two numbers have been
written down next to each other.

   commit latency makes it reachable where SQLite's does not. Bumping the
   framework pin is the fix, and is a decision for the host.
