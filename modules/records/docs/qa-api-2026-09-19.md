## 2. FAILs

### F1 — major — a field key that collides with a fixed column is silently queried against the wrong data

**Spec:** §7.2 ("if a field is declared and indexed, it *is* the query
surface"), §8.5 ("partial results returned without comment are the failure
mode worth this much ceremony").
**Probe:** `test_qa_query.py::test_BUG_field_keys_shadowed_by_fixed_columns`

`index/query.py::_term` tests `flt.field in FIXED_COLUMNS` **before** it
resolves the type's own fields, and `RESERVED_FIELD_KEYS` is only
`{"_orphaned"}` — so `status`, `display_title`, `slug`, `position`,
`published_at`, `created_at`, `updated_at` are all legal, acceptable,
indexable field keys that the query layer then answers from the
`records_record` column instead.

Requests (type `t` declares indexed `position:integer`, `slug:text`,
`status:text`; one record with `{"position": 42, "slug": "mine",
"status": "shipped"}` stored at record-column `position = 0`):

```
GET /api/records/types/t/records?filter=position:eq:42
  expected: the record (its indexed field value is 42)
  actual:   200 {"items":[],"total":0,"page":1,"page_size":25}

GET /api/records/types/t/records?filter=position:eq:0
  expected: no rows
  actual:   200, the record — matched on Record.position

GET /api/records/types/t/records?filter=slug:eq:mine
  actual:   200 {"items":[],"total":0,"page":1,"page_size":25}

GET /api/records/types/t/records?filter=status:eq:shipped
  actual:   400 {"detail":"unknown status 'shipped'","field":"status","reason":"bad_value"}

GET /api/records/types/t/records?sort=position
  actual:   200, ordered by Record.position, not by the field
```

Two of the three are a silent wrong answer with a 200 — the exact failure
shape §8.5 builds a whole 409 gate to avoid. The index rows are written
correctly; only the read path is wrong. The UI mirrors it: `FilterBar.tsx`
concatenates `indexed` fields with `fixedFilterFields(t)`, so such a key
appears twice in the filter dropdown, and `typeeditor/rules.ts::keyValid`
reserves only `_orphaned`.

Smallest fix consistent with the design: add `FIXED_COLUMNS` to
`RESERVED_FIELD_KEYS` (and to `rules.ts`), so the collision is refused at
schema-save time rather than resolved silently at query time.

### F2 — major — `on_delete` is silently unenforced when the relation field is not `indexed`

**Spec:** §9 ("Delete behaviour is a property of the field — `restrict`
(default), `set_null`, or `cascade` — enforced in the service, because there
is no foreign key to enforce it in the DB").
**Probes:** `test_qa_relations.py::test_BUG_on_delete_is_unenforced_when_the_relation_is_not_indexed`,
`::test_BUG_set_null_and_cascade_also_silently_do_nothing_unindexed`

`services/_relations.referrers()` finds referrers by querying
`records_index_ref`. Index rows exist only for fields with `indexed: true`.
`validate_fields` normalises `unique` → `indexed` for precisely this
reason (the check has nothing to read otherwise) but does nothing of the kind
for `relation`, and neither does the schema editor.

Requests (type `book` declares `author: relation → person, on_delete:
restrict, indexed: false`; one book points at Ann):

```
DELETE /api/records/types/person/records/<ann>
  expected: 409 {"detail":"1 record(s) still reference <ann>","referrers":["<book>"]}
  actual:   204 (no body)

GET /api/records/types/book/records/<book>
  actual:   200 … "data":{"t":"B1","author":{"type":"person","uuid":"<ann>"}} …
            — a live record still pointing at a trashed one
```

The same field declared `on_delete: set_null` leaves the stale reference in
the payload; declared `cascade` leaves the dependent untouched. All three
declarations are accepted by `POST /types` and all three are decorative. An
operator who unticks "indexed" on a relation — a checkbox the UI presents as
being about query performance — silently turns off referential integrity for
that field.

### F3 — major — the public read API (§10) does not exist, but the README says it does

**Spec:** §10 "Public read API"; §16 Phase 4; README §"Usage" ("a type marked
`is_public` additionally exposes an anonymous, published-only read API").
**Probes:** `test_qa_misc.py::test_public_read_api_is_absent`,
`::test_public_routes_hook_is_not_implemented`

There is no `endpoints/api/public.py` (the package docstring still says
"types, records, public … as they land"), `RecordsModule` does not override
`register_public_routes`, and `RecordsSettings.public_route_prefix` is read
by nothing.

```
POST /api/records/types  {"key":"t","is_public":true, …}   → 201, is_public: true
GET  /api/records/public/t                    (anonymous) → 404 {"detail":"Not Found"}
GET  /api/records/public/t/<uuid>             (anonymous) → 404 {"detail":"Not Found"}
GET  /api/records/public/types/t/records      (anonymous) → 404 {"detail":"Not Found"}
GET  /api/records/types/t/records             (anonymous) → 401
```

It fails **closed**, so there is no disclosure risk — the defect is that
`is_public` is a persisted, API-visible, admin-editable flag that does
nothing, and that the shipped README documents the feature as present. Also
missing with it (§9/§10): `?expand=`, and stripping `_orphaned` from a public
response (`contracts/schemas.py` explicitly defers that to "Phase 4").

### F4 — major — `allowed_roles` does not reach type deletion

**Spec:** README §Permissions — "`allowed_roles` narrows … which roles may
write records of that type on top of the static `records.edit`/
`records.manage_types` permission … The same list also governs what a delete
elsewhere may do to this type's records: a `cascade` or `set_null` relation
pointing here is refused … for a caller the list excludes."
**Probe:** `test_qa_records.py::test_manage_types_can_purge_a_narrowed_types_records`

`deps.check_type_roles` is applied on record writes only ("never on type
management"), and `services._lifecycle._role_blocked` applies it to a
*cascade* into the type — but `DELETE /api/records/types/{key}` reaches
`purge_type_records` with no role check beyond `records.manage_types`.

```
POST   /api/records/types  {"key":"t","allowed_roles":["records-editor"], …}
POST   /api/records/types/t/records            (as records-editor)  → 201
DELETE /api/records/types/t?confirm_record_count=1
         (as records-manager: has records.manage_types, not in allowed_roles)
  expected: 403 — the same caller is refused a single record write, and a
            cascade into this type is downgraded to `restrict` for them
  actual:   204 — the type and every record of it, trash included, purged
```

The narrowest path (one record write) is guarded and the widest (destroy
everything) is not. Either behaviour is defensible on its own; the
inconsistency with the cascade rule is not, and the README describes the
guarded one.

### F5 — minor — §9's `dangling: true` never appears

**Spec:** §9 — "Soft-deleting a target leaves referrers pointing at a hidden
row. Reads resolve it to `null` with `dangling: true` rather than erroring."
**Probes:** `test_qa_relations.py::test_a_soft_deleted_target_is_neither_resolved_nor_flagged`,
`::test_purging_a_referenced_target_leaves_a_dangling_reference`,
`::test_no_expand_parameter`

A reference to a trashed — or hard-purged — record reads back as the raw
stored object, with `invalid: []`, and there is no `dangling` key anywhere in
the module:

```
GET /api/records/types/book/records/<book>
  expected: "author": null  (plus a dangling marker)
  actual:   "author": {"type":"person","uuid":"<purged uuid>"}, "invalid": []
```

Reaching this state needs the referrer to be trashed first (a live referrer is
protected by `restrict`), then restored — which is an ordinary trash-and-
restore cycle. Downgraded to minor because `?expand=` is unimplemented too, so
there is no read shape for the flag to live in yet; it should not be lost when
Phase 4's expansion lands.

## 3. SPEC-GAPs (undefined behaviour a user will hit)

| # | Gap | What happens today |
|---|---|---|
| S1 | **No way to enumerate the trash.** §16/README ship "trash and restore", but `GET …/records` excludes soft-deleted rows, `is_deleted` is not a fixed column (`filter=is_deleted:eq:true` → 400 `unknown`), and `include_deleted`/`trashed`/`status=deleted` are ignored query params. A trashed record is reachable only if the caller kept its uuid; otherwise it is unrecoverable through the API. |
| S2 | **A field "rename" in one PUT is accepted.** §8.7 removes the operation precisely so it cannot silently blank a column. Sending `[{"key":"cost",…}]` in place of `[{"key":"price",…}]` classifies as destructive+additive, needs no `force` and no confirmation, returns 200, and the record then reads `"cost": null` (the old value sits in `_orphaned` after the next write). |
| S3 | **`key` in a `PUT /types/{key}` body is silently ignored.** `TypeUpdate` has no `key` field and SQLModel drops extras, so `update_type`'s "key is immutable — it is in URLs, the API and every relation target" error is unreachable over HTTP. A client that believes it renamed a type gets a 200 and no rename. |
| S4 | **Editing the slug field's value moves the record's address.** README only rules out regeneration when the *pointer* moves. Retitling a record rewrites its slug, and an edit can 409 with "slug … is already used" against an unrelated sibling. Keeping the old slug requires resending it explicitly on every subsequent write. |
| S5 | **`required` is satisfied by `""`.** `{"a": ""}` on a required `text` field returns 201 with `"a": ""`. Only `null`/absent are refused. Nothing in §6 defines this. |
| S6 | **`display_field`/`slug_field` types are unchecked.** A `json` field as `display_field` (`display_title` becomes `str(dict)` truncated to 300 chars) and a `boolean` as `slug_field` (every record's slug is `true`/`false`, so the second one 409s) are both accepted. |
| S7 | **"Separately-permissioned" destructive actions are not separately permissioned.** §8.2 says orphaned values are "purged only by a separately-permissioned action"; `orphaned:"discard"` rides on `records.manage_types`. A record hard-purge rides on `records.edit`. |
| S8 | **Unknown query parameters are silently ignored.** `?q=`, `?search=`, `?limit=`, `?offset=`, `?order=` all return a full unfiltered page with 200. `limit`/`offset` are especially likely to be guessed by a caller who has met other APIs, and they silently do nothing. |
| S9 | **`slugify` drops all non-ASCII.** "Über Straße" → `ber-stra-e`; a title with no ASCII at all yields **no slug**, so such records silently have `slug: null` and two of them never collide. |
| S10 | **View errors are JSON, not Inertia pages.** `RecordsErrorRoute` is mounted on the view router too, so `GET /admin/records/ghost` returns `404 application/json {"detail":"no record type with key 'ghost'"}`, and a malformed `filter=` on a page navigation returns a bare 400 rather than the `errors` bag the module built for exactly that case. `GET /admin/records/types` (no key) resolves to the record-list route and 404s as "no record type with key 'types'". |
| S11 | **The schema editor screen requires only `records.view`.** `/admin/records/types/{key}` renders the full type definition, `allowed_roles`, and the role list from the permission registry for any `records.view` holder; only the writes behind it need `records.manage_types`. |

## 4. Correct but surprising (usability)

- **`number` values come back as JSON strings** (`"9.99"`, `"1.23456"`). Correct
  — `to_jsonable` refuses to round-trip a `Decimal` through a float — but a
  client doing arithmetic must parse, and the field's `min`/`max` are numbers.
- **A `datetime` reads back differently from how it was stored.** The payload
  holds `2026-01-02T03:04:05+00:00`; the response serialises the coerced
  `datetime` as `2026-01-02T03:04:05Z`. Round-trips fine, but
  create-response ≠ stored bytes. On SQLite, `published_at`/`updated_at` come
  back naive after a reload, so the same instant serialises with and without a
  suffix in two consecutive responses.
- **`invalid` is always `[]` on a list response** (documented in
  `contracts/schemas.py`), so a list screen cannot show which rows a forced
  schema change broke — only opening each record does.
- **`_orphaned` is returned inside `data`** on admin reads, mixed in with live
  field keys, while writing it back is a 422. A client that reads-modifies-
  writes must strip it.
- **An empty `in` list (`filter=v:in:`) returns 200 with zero rows**, rather than
  a 400 naming the malformed term.
- **`page_size` in the response is the clamped value**, and a `page` past the end
  returns `items: []` with the true `total` — both good, neither documented.
- **409 is overloaded**: stale version (carries `current`), taken slug, duplicate
  `unique` value, restrict blockers (carries `referrers`), schema refusal
  (carries `report`), orphaned keys (carries `conflicts`) and "field is being
  reindexed" (carries `field`/`reason`) are all 409 with different bodies. A
  client has to discriminate on which extra key is present.
